# Planly 3.2 — Personal Cloud Sync Design

## Goal

Move personal Planly data from localStorage-only persistence to an authenticated Supabase-backed account while preserving Planly's current offline/local-first behaviour.

This phase is intentionally personal-only. Household sharing comes after the personal sync model is proven.

## Non-negotiable safety rules

1. Never clear the existing local Planly store as part of migration.
2. Create a complete local migration snapshot before the first upload.
3. Upload projects before tasks so project references are stable.
4. Verify cloud row counts and IDs before marking migration complete.
5. A failed migration leaves the current local app fully usable.
6. Deleted records use cloud tombstones before any later garbage collection.
7. Concurrent edits are not resolved with device clock timestamps alone.
8. Google OAuth access tokens and Google deletion queues remain device-local and are never stored in Supabase.

## Data model

### planly_projects
Cloud copy of the current local project object.

The existing local project `id` is stored as `client_id`. A separate `cloud_id` UUID is generated by PostgreSQL. This lets old installations keep their IDs while avoiding global-ID collisions between accounts.

### planly_tasks
Cloud copy of the current task aggregate.

The existing local task `id` is stored as `client_id`. Existing `projectId` and `seriesId` values are stored as client-ID references so the current application model does not have to be rewritten during migration.

Subtasks remain JSON inside the task row for 3.2. This is deliberate: Planly currently treats a task and its checklist as one editable aggregate and updates the task's `updatedAt` whenever a subtask changes. Normalising subtasks now would create avoidable partial-sync and conflict cases. We can normalise shared lists/checklists later if household collaboration requires independent subtask concurrency.

Google event identity may sync with the task. Google OAuth tokens do not.

### planly_preferences
Account copy of personal Planly settings currently saved in `planly-data-v1`.

### planly_sync_state
Account-level migration/sync metadata. It records whether initial migration has completed and the last successful sync timestamp. It does not replace local device sync metadata.

## Versioning and conflicts

Every mutable cloud record has:

- `client_updated_at`: the existing Planly millisecond timestamp for round-trip fidelity.
- `updated_at`: authoritative server receipt time.
- `cloud_version`: monotonically incremented by a PostgreSQL trigger.

Regular sync updates will use optimistic concurrency:

1. Local record remembers the cloud version it last saw.
2. Push uses `owner_id + client_id + cloud_version` as the update condition.
3. If one row updates, the write succeeded and the returned version becomes the local known version.
4. If zero rows update, another device changed the cloud record first. This becomes an explicit conflict instead of silently overwriting the newer copy.

Device clocks therefore never decide a true concurrent-edit conflict.

## Deletes

A normal user delete eventually writes `deleted_at` rather than immediately removing the cloud row.

The local UI can remove the item immediately and maintain a local pending-delete entry until the cloud tombstone is acknowledged.

A later maintenance phase can permanently purge old tombstones after an appropriate retention period.

## Initial migration protocol

### Gate 1 — account and backup

- Require an authenticated Planly account.
- Read `planly-data-v1`.
- Save an untouched migration snapshot locally under a new migration-backup key.
- Record task/project counts and IDs.

### Gate 2 — inspect cloud

- Read current cloud projects/tasks/preferences/sync state.
- If initial migration is already complete, do not re-run import.
- If cloud contains personal data while migration is not marked complete, stop and show a recovery/reconciliation state rather than automatically merging.

### Gate 3 — upload

- Insert/upsert projects.
- Insert/upsert tasks.
- Insert/upsert preferences.
- Do not mark migration complete yet.

### Gate 4 — verify

Re-read cloud data and verify:

- every local project ID exists once,
- every local task ID exists once,
- counts match,
- essential task fields round-trip,
- project and recurrence client references are preserved.

Only after verification succeeds should `initial_migration_completed_at` be set.

### Gate 5 — activate sync

localStorage remains the fast/offline working cache. Supabase becomes the authenticated canonical copy.

## Regular sync protocol

The first implementation should be deliberately conservative:

1. Load local state immediately so Planly opens offline.
2. If signed in and online, pull cloud changes since the previous successful sync.
3. Apply non-conflicting remote changes to local cache.
4. Push queued local mutations with optimistic cloud-version checks.
5. Pull once more to capture server versions and changes made during the sync window.
6. Save local state and update last-successful-sync metadata.

Do not block task creation/editing when offline.

## Local-only data

The following stay device-local in 3.2:

- Google OAuth access token
- Google OAuth token expiry
- Google delete queue
- transient open sheets/panels
- selected tab/date
- Timeline/Focus temporary UI state
- Undo timer state

## Future household compatibility

The 3.2 tables deliberately use separate server UUIDs plus owner IDs. In 3.3 we can introduce household membership/share tables without changing existing local task IDs or exposing one user's private rows to another user.

No 3.2 policy should grant another authenticated user access to an owner's personal rows.
